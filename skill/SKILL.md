# dsh-hsr-lore：星穹铁道主线剧情理解

把《崩坏：星穹铁道》主线（开拓任务）的剧情脉络、因果链与世界观概念，作为**已蒸馏的结构化知识**来查询，
而不是靠模型记忆复述。知识来自 biligame 星穹铁道 wiki（CC BY-NC-SA 4.0）。

## 1. 能力边界（先看这一节）

**能做：**

- 主线剧情问答：某章节/某任务讲了什么、关键冲突、转折与结局；
- 剧情脉络梳理：任务之间的前置/后续承接关系、跨章节因果与伏笔；
- 世界观释义：星神、命途（世界观义）、令使、派系、地点等概念的释义；
- 角色—剧情关联：主要角色在主线中的登场章节、关键行为与立场变化；
- 素材维护：按第 4 节协议补充新素材、处理纠错与冲突。

**不做（明确拒绝并说明边界）：**

- 战斗数值、光锥/遗器推荐、配队攻略、晋阶材料、模拟宇宙 buff 等**游戏机制**内容；
- **命途的战斗定位**（输出/辅助/生存/综合 这类职业分工）——属机制类；世界观义仍可回答，见第 5 节；
- 活动/限时任务（除非与主线有直接继承关系，即开拓续闻中补全主线者）；
- 主观评价：社区讨论、节奏评价、攻略建议；
- 图片、视频等多媒体资源的内容描述。

被问到机制类问题时，直接说：本 Skill 只覆盖主线剧情与世界观，不包含战斗数值与配队内容，建议查阅 wiki 对应页面。
若用户问的是**命途的世界观含义**，照常回答（走 `worldview-aeons`），并说明不是战斗定位。

## 2. 知识库状态（回答前必做）

1. 读取 `manifest.yaml`，拿到 `knowledge_version`、`last_updated` 与分片列表；
2. 按第 3 节路由匹配需要加载的分片；**不要凭记忆回答本 Skill 覆盖范围内的问题**；
3. 若某章节不在 manifest 里，如实说明「知识库尚未收录该章节」，并提示可按 `UPDATE.md` 补充，不要编造剧情。

## 3. 查询路由

用问题里的**章节名 / 地区名 / 角色名 / 事件名 / 概念名**去匹配 `manifest.yaml` 中每个分片的
`tags`、`chapter`、`entities`、`title`，命中后加载对应 `references/<file>`。

| 用户在问 | 加载 |
| --- | --- |
| 「雅利洛-VI 主线发生了什么」 | `chapter-01-jarilo` |
| 「什么是星神」 | `worldview-aeons` |
| 「什么是命途 / 令使」 | 命途的世界观义看 `worldview-aeons`（星神各执掌一条命途）；令使见 `worldview-aeons` 与 `glossary` |
| 「XX 派系是什么」 | `worldview-factions` |
| 「翁法罗斯的泰坦是什么」「谐乐大典是什么」 | 对应章节分片（`chapter-04-amphoreus` / `chapter-03-penacony`）+ `glossary` |
| 「XX 和 YY 是什么关系」 | 两角色共同登场的章节分片 + `chapter-index` 判先后 |

路由规则：

- **先章节、后概念**：问题同时含地点与概念时，先加载章节分片（剧情事实），再用世界观分片解释术语；
- **拿不准就多载**：匹配不确定时，先读 `references/chapter-index.md`（全书目、章节顺序、未收录情况），再决定加载哪些；
- **跨章节问题**：按 `chapter_order` 从小到大加载涉及的分片，回答时按主线顺序陈述，不要按用户提问顺序；
- **大分片要选择性读**：`chapter-04-amphoreus.md`（约 275KB）、`chapter-05-paradise.md`（约 194KB）、
  `chapter-03-penacony.md`（约 167KB）很大，**不要整文件读**。先用 `grep` 在该文件里按任务名/条目 ID
  （如 `quest:penacony-07`）或关键词定位，再用 `read` 的 offset/limit 只读命中的小节；
  也可以先读 `data/<分片>.json` 里的 `summary` 字段判断该读哪几条。
- **角色名走 entities**：`manifest.yaml` 每个分片都列了 `entities`（角色、地点），
  问角色相关问题时用 entities 反查该读哪个章节分片。

## 4. 更新入口

出现以下任一情况，**不要直接改 `references/` 或 `data/`**，而是按 `UPDATE.md` 走增量更新流程：

- 用户明确要求补充/更新/优化本 Skill；
- 用户给出新的 wiki 链接、新剧情文本或版本更新信息；
- 用户指出已有条目有误；
- 新主线版本发布需要新增章节分片。

要点（完整流程见 `UPDATE.md`）：原始素材先落 `inbox/YYYY-MM-DD-<slug>.md` → 按 `schemas/knowledge-fragment.schema.json`
结构化进 `data/` → 按条目 ID 合并（新条目追加、更新保留旧版到 `history`）→ **冲突不覆盖**，写入 `pending-review.md`
→ 重建对应 `references/*.md` → 更新 `manifest.yaml` 并递增 `knowledge_version` → 追加 `CHANGELOG.md` → 向用户报告变更。

## 5. 引用与边界规范

- 回答时注明来源：**biligame 星穹铁道 wiki（CC BY-NC-SA 4.0）**，并在末尾给出对应页面链接；
- 不复述为「我知道」——说清是本 Skill 蒸馏自 wiki 的条目，附 `source_url`；
- 涉及伏笔/推测时明确区分：**wiki 原文陈述** vs **本 Skill 标注的呼应关系**，不把后者说成官方设定；
- **〔归纳〕条目必须声明**：`glossary` 中标 **〔归纳〕**（数据里 `derived: true`）的条目，是对 wiki **多个页面**
  原文的归纳，**wiki 上并没有该独立条目**。引用时必须向用户说明这一点
  （例如「这是本 Skill 从 wiki 的 X、Y、Z 三处归纳的，wiki 没有同名独立页面」），并列出条目里的 `归纳自：` 来源页；
  **不得说成「wiki 上有这一条」**；
- **〔摘要由正文推导〕条目必须声明**：部分任务在 wiki 上**尚无「剧情梗概」**（新版本常见），
  其摘要由任务正文推导（数据里 `provisional: true` / `summary_source: story-derived`）。
  引用这类任务时必须说明「**该任务的 wiki 条目还没写剧情梗概，下面是依正文推导的**」，
  **不得说成 wiki 原文概要**；这类条目的 `key_points` 为空，不要凭空补关键节点；
- **⚠️ 来源冲突必须两说并列**：标 **⚠️ 来源冲突**（数据里 `conflicts` 非空）的条目，其来源互相矛盾且**尚未裁定**。
  回答时**两种说法都要讲、并分别注明出处**，绝不可只挑一种当定论，也不可自行裁定谁对；
  同时告知用户该冲突已登记在 `pending-review.md`、待确认；
- **片段是节选**：「关键片段」按剧情顺序抽样（每任务约 12 条对话 + 4 条旁白），不是该任务的全部对话，
  回答时不要说成「完整台词」；需要更多原文时读 `data/<分片>.json`（字段更全）或原始 wiki 页面；
- **命途的两义性**：wiki 的「命途」页面内容是**战斗定位**（输出/辅助/生存），属机制类、未收录。
  用户问命途的**世界观义**时，用 `worldview-aeons`（各星神执掌一条命途）与章节正文里的释义回答，
  并说明这是关于命途的世界观含义，不是游戏里的战斗定位；
- **不臆造**：`references/chapter-index.md` 标为「未收录」的章节、或 manifest 里没有的条目，
  一律如实说「知识库未收录」，不得凭模型记忆补写剧情；
- 仅在个人/研究用途下使用本 Skill 的知识，不做商业用途。

## 6. 目录结构

| 路径 | 作用 |
| --- | --- |
| `SKILL.md` | 本文件：能力、路由、更新入口、引用规范（逻辑层） |
| `UPDATE.md` | 增量更新与优化协议（收到新素材时读它） |
| `manifest.yaml` | 分片清单、版本号、路由用的 tags/entities（**路由的唯一依据**） |
| `references/` | 可读知识分片（回答问题主要读这里） |
| `data/` | 结构化源数据（更新合并的依据，字段见 `schemas/`） |
| `inbox/` | 新素材收件箱（原始素材先落这里，不直接改知识文件） |
| `pending-review.md` | 冲突与待复核条目 |
| `CHANGELOG.md` | 每次更新的留痕记录 |
